# XacReBook — Live Book Auction

A book-selling website where every book is sold to the highest bidder. Anyone can
browse the catalog freely; signing in (name + phone number) is only required to
place a bid. Bids update live for everyone watching a book.

## Stack

- **Client**: React + Vite + TypeScript, Tailwind CSS, Framer Motion, Socket.IO client
- **Server**: Node.js + Express + TypeScript, Socket.IO, Prisma ORM
- **Database**: PostgreSQL
- In production the server serves the built client itself (same origin), so there's
  no CORS or cross-site-cookie configuration to fight with — one deployable unit.

## Project layout

```
/client   React app (Vite)
/server   Express API + Socket.IO + Prisma schema
docker-compose.yml   local Postgres for development
```

## Local development

### 1. Start Postgres

```bash
docker compose up -d
```

This starts Postgres on **localhost:55432** (not the default 5432, to avoid clashing
with any Postgres already installed on your machine). Data persists in a Docker volume.

### 2. Server

```bash
cd server
cp .env.example .env      # edit JWT_SECRET before deploying anywhere real
npm install
npx prisma migrate dev --name init   # creates tables
npm run seed                          # creates an admin user + sample books
npm run dev                           # http://localhost:4000
```

The seed script prints the admin login it created (default `admin` /
`changeme123` unless overridden by `SEED_ADMIN_USERNAME` / `SEED_ADMIN_PASSWORD`
in `.env`). **Change the seeded admin password before the site goes live.**

### 3. Client

In a second terminal:

```bash
cd client
npm install
npm run dev   # http://localhost:5173
```

Open http://localhost:5173 — the Vite dev server proxies `/api` and `/socket.io`
to the Express server on port 4000, so it behaves like one app.

### Everyday flow

- Browse the Home page and Library without signing in.
- Click "Sign in" or try to place a bid to trigger the sign-in modal (name + phone).
- Go to `/admin`, log in with the seeded admin account, and add real books
  (cover image URL or file upload, genre, starting price, bid increment,
  auction end time).
- Open a book in two browser windows and place a bid in one — the price and
  leaderboard update live in the other via Socket.IO.

## How bidding stays correct under load

Placing a bid runs inside a single Postgres transaction that takes a row lock
(`SELECT ... FOR UPDATE`) on the book being bid on, re-checks the current price,
and only then inserts the bid and updates the price. If two people bid at the
exact same instant, the database serializes them — the second bid is
re-validated against the price the first bid just set, so nobody can "win" a
bid that was already beaten. This matters more than the UI once there are
hundreds of people bidding at once. See `server/src/routes/bids.ts`.

Bid submission is also rate-limited per IP (8 bids / 10s) to blunt accidental
double-submits or scripted spamming during the live event.

## Deploying for the live event

The goal is one thing that is boring and hard to knock over for 48 hours, not
the cheapest possible setup. Recommended: **Render.com**, one Web Service +
one managed Postgres instance — provisioned together from the `render.yaml`
Blueprint in this repo.

1. Push this repo to GitHub:
   ```bash
   git add -A
   git commit -m "Deploy XacReBook"
   git push -u origin main
   ```
2. On Render: **New +** → **Blueprint** → connect the GitHub repo. Render reads
   `render.yaml` and provisions the Postgres database and the web service
   together, pre-wired to each other.
3. It'll prompt for two secrets it can't generate itself:
   - `SEED_ADMIN_USERNAME` / `SEED_ADMIN_PASSWORD` — your real admin login.
     (`JWT_SECRET` is auto-generated by the blueprint; `DATABASE_URL` and
     `CLIENT_ORIGIN` are wired up automatically — nothing to fill in for those.)
4. Click **Apply**. First deploy will build both `client` and `server`, then
   run `prisma migrate deploy` before starting — the database needs a minute
   to finish provisioning first, so if the very first deploy fails because the
   DB wasn't ready yet, just hit **Manual Deploy** again.
5. Once it's live, run the seed script **once** from the Render shell (Dashboard
   → your service → **Shell**) to create the admin user and sample books:
   `npm run seed --prefix server`
6. **Instance plan**: the blueprint defaults both the web service and database
   to Render's `starter` plan (paid, always-on — never the free tier, which
   spins down on idle and would drop every open Socket.IO connection). Bump
   the web service to `standard` from the Render dashboard for the actual
   event day if you're expecting the full "hundreds of concurrent users" load,
   then scale back down afterward. Scale the plan up, not out to multiple
   instances — Socket.IO rooms are simplest on one instance.
7. **Cover images**: uploaded covers are stored on local disk
   (`server/uploads`) and served at `/uploads/...`. Render's disk is
   *ephemeral* — it's fine for a 1–2 day event as long as you don't redeploy
   after uploading covers (redeploys reset the filesystem). If you'll be
   redeploying during the event, use image URLs instead of file upload (the
   admin form accepts a plain URL), or wire up a Render persistent disk /
   object storage (S3, Cloudinary) — not set up here to keep the stack
   simple, since it wasn't required for a 1–2 day run.

### Before the doors open

- Make sure `SEED_ADMIN_USERNAME` / `SEED_ADMIN_PASSWORD` were set to real
  values (not `admin` / `changeme123`) before running the seed script.
- Load-test the bid endpoint so "hundreds of users at once" isn't a surprise:

  ```bash
  npx autocannon -c 200 -d 20 -m POST \
    -H "Content-Type: application/json" \
    -b '{"amount": 999999}' \
    https://your-app.onrender.com/api/books/<a-real-book-id>/bids
  ```

  (Expect most of these to fail with 400/401 since they're unauthenticated
  junk bids — the point is confirming the server stays up and responsive
  under concurrent write load, not that the bids succeed.)
- Open the site on a phone and a laptop and place a real bid end-to-end.

## Known trade-offs (intentional, given the 1–2 day scope)

- No SMS/OTP verification on sign-in — name + phone is trust-based, matching
  what was asked for. Anyone could type someone else's phone number; that's an
  acceptable risk for a short live event, not a production identity system.
- Cover images on local disk rather than object storage (see above).
- `express` 4.x pulls in a `qs` version with a known moderate-severity
  advisory (DoS via crafted query strings); no fix is available without a
  major Express 5 upgrade. Left as-is to keep the stack battle-tested for a
  tight deadline — worth revisiting after the event.
